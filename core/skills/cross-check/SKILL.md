# Кросс-чек: один ИИ делает, второй проверяет, человек принимает

Основной ИИ делает работу, второй проверяет (кто именно, написано в `.workplace/config.json`: `main` и `reviewer`; узнать: `node .workplace/core/cli/wp.js config show`). Проверяющий читает и ничего не правит, правки делает автор. Вердикт проверяющего повторно моделью не проверяют. Если тебя запустили как проверяющего, этот навык не вызывай: дай вердикт по файлам из текущей папки.

Работай из главной папки (там `AGENTS.md`, `.workplace/` и `checks/`). Скрипты только на встроенных модулях Node, команды одинаковы на Mac и Windows и для обоих ИИ.

## Что важно знать

- **Когда запускать.** По слову «кросс-чек», по просьбе человека, по умолчанию перед отправкой наружу. Человек сказал «без проверки» или «не проверяй»: не запускай, сделай действие и в итоге напиши «не проверено вторым ИИ по слову человека». Сторож кросс-проверки видит эти слова сам.
- **Предупреждения вместо вопросов.** Скажи одной строкой: «Проверю N файлов, это один запуск, он тратит лимит проверяющего». Файлов больше 5 или больше 100 КБ: добавь, что это дольше и дороже, и запускай. Ответа «да» не жди.
- **Что уходит наружу.** Файлы проверки уходят в сервис вендора проверяющего (OpenAI для Codex, Anthropic для Claude). Проверяющий получает не папку, а **копии явно названных файлов**; читать вне копий ему сказано в запросе. Назови человеку, что уйдёт.
- **Что скрипт не берёт:** `.env` и файлы ключей, закрытые ключи, `.git/`, `node_modules/`, `checks/`, ссылки, бинарные файлы (Word, Excel, PDF, картинки: сохрани как `.md`, `.csv`, `.txt`). Нашёл в тексте похожее на ключ или пароль: скрипт назовёт строки без значений; замени секрет заглушкой в копии.
- **Принимается.** Тексты и таблицы (`.md`, `.txt`, `.csv`, `.json`, `.html`, `.yaml`) и код на любом языке. До 30 файлов, до 400 КБ каждый, до 1,5 МБ всего: файл больше режь на куски.
- **Файлы вне главной папки.** Человек назвал файл или папку проекта в другом месте: скопируй нужные текстовые файлы в `workspaces/review-copies/data/<имя>/` (команда копирования оболочки; `.env` и ключи не бери), а в `--result` передай пути копий. Оригинал не меняется. В сводке скажи, что проверена копия на такую-то дату.
- **Персональные данные.** Почты и телефоны в копиях маскируются (`i***@домен`, `+*** *** ** 42`), даты и номера документов остаются. Настоящие контакты проверяющему только по слову человека (шаг 0).

## Шаг 0. Данные для проверяющего

Если `checks/POLICY.md` нет, один раз скажи: «Файлы уходят в сервис второго ИИ. Настоящие почты и телефоны я скрываю звёздочками. Если нужно показать их проверяющему, скажите». Запиши строку `ПДн проверяющему: нельзя (маскируем), решение по умолчанию, <дата>`. Человек разрешил: `ПДн проверяющему: можно (<кто решил>, <дата>)`. Границы чтения у проверяющего нет, есть запрос и копии: скажи это честно.

## Шаг 1. Что проверяем

Два режима. **Результат**: работа сделана (файлы). **Намерение**: шаг ещё не сделан, это план, письмо, команда, список получателей. Определи: (а) файлы или текст шага; (б) задачу автора одной фразой; (в) источники для сверки (для кода: описание задачи, тесты, соседние файлы). Чего-то не хватает: один вопрос человеку.

## Шаг 2. Подготовка папки проверки

```
node .workplace/core/skills/cross-check/scripts/prepare-check.js --name короткое-имя --task "одна фраза" --result путь1,путь2 --sources путь3,путь4
node .workplace/core/skills/cross-check/scripts/prepare-check.js --name письмо --action "отправить письмо клиенту по списку из рассылки" --result письмо.md --sources список.csv
```

Первая команда для результата, вторая для намерения (`--action` описывает шаг, текст кладётся в `result/action.md`; текст письма, план или команду передай файлом через `--result`). Скрипт создаёт `checks/<дата-время-имя>/` с `input/` (копии), `manifest.json` (пути и sha256 оригиналов) и `prompt.md`. Повторная проверка после правок: `--retry`. Намеренное, что похоже на ошибку: `--known "..."`, чтобы не получить ложный RED.

## Шаг 3. Запуск проверяющего

```
node .workplace/core/skills/cross-check/scripts/run-check.js checks/ПАПКА
```

Скрипт копирует `input/` в `checks/<папка>/run-copy/`, запускает проверяющего через `core/providers/<reviewer>` (режим чтения, правила рабочей папки он не видит, модель из `config.json`, по умолчанию не задана), пишет ответ в `verdict.md`, ход работы в `review.log`, по таймауту (540 с, `--timeout` меняет) останавливает проверяющего вместе с дочерними процессами. Малую проверку запускай с таймаутом оболочки 600 с. Большую запускай в фоне с `--timeout 1500` и жди `verdict.md`; второй запуск параллельно не начинай. Не вышло: `--in-place`.

Основной ИИ Codex: проверяющий Claude вызывается из песочницы Codex, а у неё по умолчанию нет сети. `wp.js layout` пишет в `<корень>/.codex/config.toml` настройку `[sandbox_workspace_write]` `network_access = true` (Codex нужно перезапустить; запасной путь: запустить Codex с `-c sandbox_workspace_write.network_access=true`). Без сети `run-check.js` за несколько секунд отвечает «нет сети» и называет, что включить.

## Шаг 4. Принять вердикт

Код возврата проверяющего ничего не доказывает: без нужных прав он «не мог прочитать файл» и всё равно завершался кодом 0. Принимает проверку скрипт:

```
node .workplace/core/skills/cross-check/scripts/finalize-check.js checks/ПАПКА
```

Он проверяет: рядом лежит `run.json` от `run-check.js` (проверяющий из `config.json`, код выхода 0, хеши `verdict.md` и `prompt.md`, время запуска после подготовки), вердикт не пуст, первая строка `ВЕРДИКТ: GREEN|YELLOW|RED`, нет `???`, в разделе «Прочитано» по каждому файлу есть **верная** цитата, оригиналы не менялись. Вердикт, написанный руками без запуска проверяющего, не принимается (`НЕ ПРОВЕРЕНО`), а запись в `verdict.md`, `run.json`, `manifest.json`, `review.log`, `prompt.md` сторож останавливает: так проверка остаётся честной. Принято: в манифесте `status: checked`. Нет: `НЕ ПРОВЕРЕНО`, результат не выдавай за проверенный. Причины и что делать: вывод скрипта, `review.log`, `.workplace/docs/troubleshooting.md`. Повтори один раз; не помогло, смени способ (`--in-place`, меньше файлов, повтор после возврата лимита) и расскажи человеку, что случилось и что предлагаешь. Решение «идти без проверки» принимает человек своими словами.

## Шаг 5. Что сказать человеку

Короткая сводка (5-8 строк), заголовок «Что нашла вторая модель»: вердикт и что проверено; каждая находка (где, что не так, блокирующая или нет); отдельно «Позиция основного ИИ» и «Позиция проверяющего», если не согласен (аргумент и источник); путь к `checks/ПАПКА/verdict.md`.

## Шаг 6. Что делать с вердиктом

- GREEN: можно показывать как проверенное; для намерения можно выполнять.
- YELLOW: неблокирующие замечания. Исправь очевидное и безопасное, остальное перечисли.
- RED: сверь каждую находку с источником сам (проверяющий тоже ошибается). Подтверждённые исправь, неподтверждённые перечисли с аргументом, затем один повторный запуск (`--retry`). Снова RED: покажи оба вердикта и спроси человека. Для намерения RED значит «шаг выполнять после исправления».
- Третий круг обычно не нужен: решай вместе с человеком. Любая правка меняет sha256: файл считается непроверенным, пока не пройдёт повтор или человек не примет его без проверки. В конце добавь в `tasks.md` строку: дата, что проверяли, вердикт, путь к папке проверки.

## Проверка настройки рабочего места (по запросу)

`prepare-check.js ... --profile setup-review`: профиль добавляет в запрос список намеренного (сторожа, флаги в `config.json`), чтобы не получать ложный RED. В источники положи `AGENTS.md` и `.workplace/config.json`.

## Самопроверка: проверяющий должен уметь краснеть

Нужна при установке (она входит в план, отдельного «да» не нужно), после смены основного ИИ и после серьёзных изменений: два запуска проверяющего, данные вымышленные.

```
node .workplace/core/skills/cross-check/scripts/selftest-run.js
```

Скрипт кладёт в `selftest/` источник, верную копию и копию с вшитой ошибкой (у Беты 4,0 вместо 2,0) и проходит шаги 2-4 по каждой. Ожидаемо: верная принята как GREEN (YELLOW допустим); с ошибкой принята как RED, в находках названы Бета и 4,0 (`finalize-check.js --expect-mention "Бета|4,0" --expect-verdict RED`). GREEN или нет названной ошибки значит, что проверка слепая: скажи человеку «проверка не работает» и чини её, прежде чем полагаться на неё. Скажи человеку: «вторая копия заведомо неверная, она нужна, чтобы проверить, что проверяющий ловит ошибки». Файлы `selftest/` не удаляй.
